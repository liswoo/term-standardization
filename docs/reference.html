모듈책임
naming.pyKiwi 형태소 분석, 명명 규칙(길이/문자종류/조사) 검증, strip_trailing_particle(결정론적 조사 제거), unmatched_spans/split_into_nouns(용어명에서 표준단어로 분해 안 되는 부분 추출 및 다중명사 분리, 2026-09-16), segment_words(완전분해 체크).
search.py / embeddings.py정규화 RDB 검색(trigram+명사토큰), 로컬 임베딩(multilingual-e5-small)+pgvector 코사인 검색. search()(용어), search_words()(의미로 단어 찾기), search_terms_by_meaning()(의미로 용어 찾기, find_term용), 후보 병합·중복제거.
guideline.pystandard_guide.md를 벡터화한 guideline_chunks 기반 RAG 준수 검사. 형태소 규칙은 코드가, 의미 판단(포괄적 단어 등)만 이 모듈이 담당. matched_forbidden_word를 먼저 선언시켜 코드가 최종 판정을 덮어씀(아래 "작은 모델" 패턴).
abbreviation.py용어 영문 약어 추천(RAG+기존 약어 일관성)과 형식/고유성 검증. 대규모 카탈로그에서는 기존 약어 전체 대신 이름 유사도(pg_trgm) 상위 200건만 프롬프트에 넣음(스케일 버그 수정).
definition_suggestion.py용어 정의 초안 제안. 이름이 진짜 애매하면(카탈로그 내 이미 갈라진 개념과 겹칠 때) 추측 대신 확인 질문+후보를 먼저 냄. clarification_history(질문·답변 전체 이력)를 받아 여러 라운드 명확화 지원.
word_suggestion.py단어 등록은 이름이 아니라 의미가 입력 — suggest_word()가 기존 단어와의 일치 여부를 다른 무엇보다 먼저 판단하도록 스키마 순서로 강제. fixed_name으로 제안 이름이 용어의 실제 표기에서 절대 벗어나지 않게 강제(2026-09-16, 리네이밍 드리프트 방지).
domain_suggestion.py(2026-09-21) suggest_domain()이 용어의 정의문에서 신규 도메인 스펙(데이터유형/길이/허용값 등)을 초안 — word_suggestion.py와 동형의 강제 중간 필드(existing_domain_match)로 재사용/신규 주장을 동시에 못 하게 막음. 도메인엔 임베딩이 없어 안전 재확인은 유사도 검색 대신 활성 도메인 전체를 후보로 씀. rationale이 정의문 속 근거를 못 대는 필드는 애초에 제안하지 않도록 강제. conversation.py의 request_new_domain/confirm_domain_spec/set_domain_pii 인텐트로 챗봇에 연결됨 — 아키텍처 문서 참고.
comparison.py기존 용어와의 정의 비교(SAME_MEANING/RELATED_BUT_DISTINCT/UNCERTAIN), 콘텐츠 기반 캐시(comparison_cache).
registration.py용어 등록: 검증 스냅샷(prepare), 최종 확인(submit), 검토 대기 중복 조회(find_pending), 관리자 승인(approve, CLI 전용). 로컬 LLM 테스트 시 비교 후보를 LOCAL_COMPARE_CANDIDATE_CAP으로 제한(운영 경로엔 적용 안 됨).
word_registration.py단어 등록: registration.py와 완전 대칭인 prepare/submit/approve. approve()는 그 단어를 기다리던 용어의 의존 관계도 같이 확인해서, 전부 승인됐으면(그리고 도메인 의존성도 없으면, 2026-09-21) 용어를 WAITING_FOR_WORD_APPROVAL에서 풀어줌.
conversation.pyDify가 해석한 의도의 상태 전이(transition)와 revision 충돌 검출(apply). 단계 순서는 아키텍처 문서 참고.
tools.pyMCP 도구 29개 등록, 공통 에러 래핑(@tool 데코레이터). 아래 표 참고.
schemas.py구조화 LLM 출력/도구 입력 Pydantic 모델. 필드 선언 순서가 실제로 모델 판단 순서에 영향을 줌(작은 모델에게 중간 판단을 먼저 강제시키는 패턴, 여러 모듈에서 재사용).
db.pyPostgres 연결(psycopg), 마이그레이션 실행, catalog_fingerprint()(카탈로그 변경 감지용 해시 — 안 바뀐 행까지 건드리면 진행 중 등록이 전부 무효화되므로 idempotent 임포트에 필수).
credentials.pyOpenAI/로컬(Ollama) LLM 런타임 전환(active_provider(), .runtime/llm_provider.json). provider별 타임아웃(OpenAI 35초/로컬 90초), 로컬 전용 extra_body={"think":False}.
auth.py비밀번호 해싱(PBKDF2-HMAC-SHA256, stdlib) + 세션 발급/조회(sessions 테이블, 랜덤 토큰). require_auth/require_admin 헬퍼, active_admin_count()(마지막 관리자 보호).
admin_api.pyMCP 서버(포트 8100)의 REST 라우트: /admin/llm-status·/admin/llm-provider(LLM 전환), /admin/auth/*(로그인/가입/세션/회원관리/비밀번호변경), /admin/domain-requests*·/admin/mock-tables·/admin/domains/{code}/sample-data(도메인 신청·개인정보 샘플조회, 2026-09-17), /admin/standard-data(용어/단어/도메인 통합 조회, 2026-09-17), /admin/term-requests·/admin/word-requests(용어/단어 간편 입력 신청, 2026-09-17), /admin/domains/{code}(도메인 상세 - 허용값/표현형식/저장형식/데이터유형 등, 2026-09-18 - 용어 신청 폼의 도메인 참고값 자동표시와 챗봇 등록완료 카드가 같이 씀), /admin/term-requests/check-name·/admin/term-requests/suggest-definition·/admin/term-requests/suggest-followups(간편 입력 폼의 실시간 이름 중복 확인·정의/도메인/영문약어 추천, 2026-09-21 - 전부 읽기전용, 챗봇이 쓰는 search()/suggest_definition()/domain_usage()/suggest_abbreviation()을 그대로 재사용), /admin/chat·/admin/list-terms(Dify 프록시, 2026-09-22 - 프론트가 더 이상 Dify API 키를 안 들고 있고, 세션으로 인증한 뒤 서버가 .runtime/chatflow-key.txt/.runtime/list-terms-key.txt의 실제 키로 대신 호출·중계; user는 클라이언트 값을 무시하고 세션의 실제 사용자명으로 강제). Caddy가 /admin/*를 프론트와 같은 오리진으로 프록시.
domain_registration.py도메인 신청(버튼 기반 직접 폼)의 prepare()/submit()/approve()/reject() — word_registration.py와 같은 2단계 확인 패턴이지만 임베딩·의미비교 없음(코드 유일성만 확인). approve()는 이제(2026-09-21) word_registration.approve()와 대칭으로, 이 도메인을 기다리던 WAITING_FOR_DOMAIN_APPROVAL 용어도 같이 승격시킴(단어 의존성도 없을 때만).
quick_registration.py"표준 데이터 조회"의 "용어 신청" 탭 간편 입력 전용(2026-09-17). prepare_term()이 registration.py의 prepare()/submit()을 그대로 위임하므로 임베딩+LLM 의미비교·가이드라인 검사는 챗봇 경로와 동일 — 다만 conversation.py의 confirm_term이 하던 표준단어 완전분해(word gap) 체크만 직접 재현해서, 챗봇의 단어등록 서브플로우 없이는 처리 못 하는 이름은 WORD_GAP_REQUIRES_REGISTRATION으로 먼저 걸러낸다. 단어 신청은 이 모듈 없이 word_registration.py를 그대로 씀(원래도 exact-match만 확인하는 단순 경로라 도메인과 동급).
unified_catalog.py"표준 데이터 조회" 통합 화면(2026-09-17) 전용. list_standard_data()가 standard_terms/standard_words/domains 각각과 그 대기 신청 큐를 kind로 태그해 최대 6개 UNION ALL 브랜치로 합쳐 한 번에 정렬/검색/페이지네이션. 각 브랜치는 반드시 동일한 컬럼 별칭(AS kind, id, logical_name, ...)을 명시 — 필터로 어느 브랜치가 먼저 오든 컬럼명이 안 바뀌게 하기 위함(생략하면 UNION 첫 브랜치의 별칭 없는 컬럼명이 전체에 적용되어 프론트에서 값이 죄다 undefined로 깨지는 버그가 실제로 있었음). TERM 브랜치는 domains를 LEFT JOIN해서 valid_values/display_format은 용어 자신의 값이 있으면 그걸(COALESCE), 없으면 도메인 값을 보여주고, storage_format/data_type/data_length/decimal_length/unit은 항상 도메인에서 그대로 가져온다(2026-09-18 - 이 5개는 용어 자체엔 애초에 저장하지 않음).
mock_operations.py가상 운영 데이터 조회. ALLOWLISTED_MOCKOPS_TABLES가 유일한 진입점 — table_name/column_name은 이 화이트리스트를 통과해야만 SQL에 들어감(파라미터 바인딩 안 되는 identifier라 f-string 조립, 반드시 검증 필요).
config.py환경변수 로드(.env), 모델 이름/경로 상수.

파일역할
index.html메인 앱 셸. 로그인 카드(#auth-shell) + 사이드바/상단바 고정 SaaS 레이아웃 + 3개 화면(대시보드/표준 데이터 조회/설정) + 챗봇 패널. 용어사전·단어사전·도메인관리 3개 화면은 2026-09-17에 "표준 데이터 조회" 하나로 통합됐고, 그 안에 다시 조회/용어 신청/단어 신청/도메인 신청 4개 탭이 있다(같은 날 두 번째 변경 — 독립 화면이던 "도메인 신청"도 이 탭 구조로 흡수됨, 아래 app.js 설명 참고).
app.js인증 게이트(requireAuth/showApp), 뷰 전환(switchView), 대시보드 통계용 백엔드 조회(fetchCatalogFromBackend → 목록조회 워크플로우, state.terms/state.domains는 대시보드 카드·차트 전용으로 유지), 챗봇 SSE 스트리밍 + 구조화 카드 렌더러(renderStructuredBlock), 필터 바인딩(bindFilterControls), 개인정보 도메인의 샘플 데이터 조회(showDomainSampleData, 2026-09-17). "표준 데이터 조회" 통합 화면(2026-09-17)은 fetchUnifiedCatalog/renderCatalogTable이 별도로 /admin/standard-data REST를 호출 — 옛 renderTermsTable/renderWordsTable/renderDomainGrid는 삭제됨(단, renderTermsTable이 같이 갱신하던 stat-total-terms 대시보드 카드 줄만 renderAll()로 이관). 그 화면 안 상단 탭(switchCatalogTab, 2026-09-17): "조회"(기존 표) 외에 "용어 신청"/"단어 신청"/"도메인 신청" 3개 탭이 같은 view 안에서 패널만 바뀐다 — 각 신청 탭은 간편 입력 폼(/admin/term-requests·/admin/word-requests·/admin/domain-requests)을 제공하고, 단어 신청 탭은 추가로 "AI와 대화하며 등록" 버튼(기존 플로팅 챗봇을 그대로 열어 submitChatMessage("단어를 등록할래요")를 대신 보내는 것뿐, 새 챗 로직 없음)을 둔다. 용어 신청 탭은 그 버튼을 없애고(2026-09-21, 헤더의 "신규 용어 등록"과 중복) 대신 AI 추천 ON/OFF 토글(setTermAiAssist/termAiAssist), 헤더 우측 상단 초기화 아이콘(resetTermRequestForm), 제출 시 칸별 빨간 테두리(validateTermForm/TERM_ERROR_FIELDS)를 둔다. 도메인 신청 폼은 예전 독립 view-domain-request 화면에서 이 탭으로 그대로 이전됨(엘리먼트 id 불변). 용어 신청 폼의 허용값/표현형식/저장형식은 읽기전용 참고 필드(populateTermDomainDerivedFields, 2026-09-18) - 도메인 입력에 타이핑하면 fetchDomainDetail()로 /admin/domains/{code}를 불러와 자동으로 채워 보여주고, 제출 payload엔 포함하지 않는다("도메인이 결정하는 값"이라 신청자가 입력할 필요가 없다는 원칙). 같은 fetchDomainDetail()을 챗봇의 등록완료 카드(renderRegistrationCard, 이제 async)도 써서 대화 중엔 묻지 않은 도메인 전체 스펙(도메인그룹/분류/데이터유형/길이/저장형식/표현형식/단위/허용값)을 완료 시점에 보여준다 — renderStructuredBlock도 이 때문에 async로 바뀌었고 호출부(submitChatMessage)가 await한다.
