    term-standardization-ui/    <- 정적 프론트엔드. 순수 HTML/CSS/JS, 빌드 스텝 없음.
      ├─ index.html   메인 앱(대시보드/사전/도메인관리/설정 + 채팅 패널)
      └─ members.html 회원 관리 전용 창(관리자 전용, 새 창으로 열림)

dify 폴더는 "엔진", term-standardization은 그 위에 얹은 업무 로직 + 자동화 + 프론트입니다. Dify 안의 앱/지식베이스/API 키/모델 자격증명은 설치본마다 새로 생기는 Dify 자체 DB 데이터라 설치본 간 이전이 안 됩니다 — setup_dify.py가 이 부트스트랩 전체를 자동화합니다.

요청이 실제로 흐르는 경로

사용자 동작경로
챗봇으로 용어/단어 등록UI → Dify Chatflow(용어표준화-대화형) → CLASSIFY(의도해석) → MCP apply_dify_turn → conversation.transition() → RENDER(답변 생성)
대시보드 통계/차트UI → Dify 워크플로우(용어표준화-목록조회, 대화 상태 없음) → MCP list_terms/list_standard_words/list_data_domains
로그인/회원가입/회원관리/LLM 전환/용어·단어·도메인 신청/표준 데이터 조회UI → Caddy가 /admin/*를 MCP 서버(포트 8100)의 admin_api.py로 그대로 프록시 (Dify를 거치지 않음, 순수 REST). 도메인 신청은 코드 유일성만 확인하는 단순 경로(2026-09-17). 용어/단어 "간편 입력" 신청(2026-09-17, 같은 날 두 번째 추가)은 /admin/term-requests·/admin/word-requests가 registration.py/word_registration.py의 prepare()/submit()을 그대로 태우므로, 챗봇 경로와 동일한 품질 검증(용어는 임베딩+LLM 의미비교까지)을 REST 한 번으로 수행한다 — 다단계 안내 없이 실패 사유를 한 번에 반환하는 점만 챗봇과 다르다. "표준 데이터 조회"(용어사전/단어사전/도메인관리 3개 화면을 통합, 2026-09-17)는 /admin/standard-data(unified_catalog.py)를 호출 — 대시보드와 달리 워크플로우를 거치지 않음. 이 네 신청 경로 모두 같은 "표준 데이터 조회" 화면 안 탭(조회/용어 신청/단어 신청/도메인 신청)으로 묶여 있고, 각 신청 탭은 간편 입력 대신 기존 플로팅 챗봇을 그대로 여는 "AI와 대화하며 등록" 버튼도 같이 제공한다.

업무 판단과 저장의 기준은 항상 MCP이고, Dify의 LLM 노드는 의도 해석과 답변 문장 생성만 담당합니다. 목록조회는 챗플로우와 완전히 별개의 Dify 앱이라 배포도 별개입니다.

회원 관리가 별도 창인 이유 members.html은 index.html과 같은 세션 쿠키를 공유하는 독립 페이지입니다(2026-09-17). 관리자만 보이는 "회원 관리" 버튼이 window.open()으로 열고, 그 페이지 자체가 다시 /admin/auth/me로 관리자 여부를 확인합니다 — 프론트에서 버튼을 숨기는 것과 별개로, 페이지 자체도 스스로를 지킵니다.

대화 상태머신

term_service/conversation.py의 transition(state, action, ...)이 순수 함수로 모든 단계 전이를 결정합니다. Dify는 사용자 메시지를 {intent, value, confirmed}로만 해석해서 넘기고, 실제 유효성 검사·중복 판정·저장은 전부 이 함수와 그 안에서 호출하는 모듈이 합니다. 프론트엔드는 이 순서와 무관합니다 — app.js의 카드 렌더러는 stage 이름과 그 stage가 들고 있는 state 필드만 보고 그리므로, 상태머신 순서를 바꿔도 프론트는 대체로 손댈 필요가 없습니다.

propose_term → awaiting_term_confirm → confirm_term
  → (EXACT_MATCH/SYNONYM_MATCH) → existing_term_found  [종료]
  → (검토 대기 중복) → pending_request_found  [종료]
  → (형태소/가이드라인 위반) → awaiting_guideline_choice → propose_term로 재시도
  → (이름이 표준단어로 완전분해 안 됨)
      → awaiting_word_split_choice (하나로/여러 단어로 쪼갤지 선택)
          → awaiting_word_meaning [단어 등록 서브플로우, 단어별로 반복] → 전부 완료 후 복귀
  → awaiting_definition (정의 제안/명확화 질문)
      → set_definition → awaiting_domain_choice (이름+정의로 검색한 근거로 도메인 추천)
          → set_domain → registration.prepare() 호출 시점
              → (SAME_MEANING/GUIDELINE_VIOLATION/SYNONYM_CONFLICT) → definition_blocked  [종료]
              → awaiting_abbreviation (영문약어 제안)
                  → set_abbreviation → awaiting_confirm
                      → confirm_registration → submitted | registration_failed  [종료]

── 독립 진입: 단어를 바로 등록하고 싶을 때 ──
propose_word → confirm_word
  → (기존 단어와 의미 일치) → word_reused  [종료]
  → (신규) → awaiting_word_abbreviation → set_word_abbreviation → word_submitted  [종료]

── 독립 진입: 이름이 아니라 의미로 기존 용어 찾기 ──
find_term → search_terms_by_meaning() 결과만 보여주고 종료 (등록 아님)

왜 정의가 도메인보다 먼저인가 — 원래는 도메인을 먼저 물었지만, 그 시점엔 비교군 검색 신호(용어명 하나뿐)가 약했습니다. 실측: "주간식단"을 이름만으로 검색하면 코사인 유사도 0.838(임계값 미만), 이름+정의로 검색하면 0.910. 그래서 정의를 먼저 받고 그 정의까지 포함한 검색으로 도메인을 추천하도록 순서를 바꿨습니다(2026-09-10, 상세는 변경 이력). registration.prepare()(SAME_MEANING/구문 검증)는 이름+정의+도메인이 모두 있어야 호출되므로 지금은 set_domain에서 실행됩니다.

단어 서브플로우 진입점이 두 개입니다: (a) 임베디드 진입 — 용어 등록 중 이름이 표준단어로 완전분해 안 되면 자동 분기, state["resume_term"]에 원래 진행 상황을 저장해두고 끝나면 복귀. (b) 독립 진입 — propose_word로 처음부터 단어만 등록. 용어 하나가 여러 단어 승인을 동시에 기다릴 수 있어서(2026-09-16), 의존 관계는 다대다 테이블 registration_request_word_dependencies로 추적합니다 — reference.html 참고.

abbreviation_aliases영문 약어 ↔ 한글 이름 별칭 매핑(약어 추천 근거).
comparison_cachecompare()(정의 비교 LLM 호출) 결과의 내용 기반 캐시 — 같은 비교 재호출 방지.
guideline_chunksstandard_guide.md를 섹션별로 벡터화. 가이드라인 준수 검사/약어·정의 추천의 RAG 근거.

mockops_customers가상 운영 데이터(합성, SYNTHETIC_MOCKOPS_NOT_REAL) — "개인정보여부" 플래그가 가리킬 실제 대상. manage.py seed-mockops로 시딩.

두 개의 독립된 벡터/RAG 시스템 — 절대 섞지 마세요

  1. MCP 자체 pgvector(embeddings.py, search.py, guideline.py) — standard_terms(용어 유사도/중복 판정), guideline_chunks(가이드라인 준수 검사·약어·정의 추천 근거), standard_words(의미로 기존 단어 찾기)를 담당. 이게 업무 판단의 기준입니다.
  2. Dify 자체 지식베이스(sync_dify_knowledge.py가 Weaviate에 업로드) — show_candidates/help 의도일 때만 참고 자료로 노출되는 보조 지식. 업무 판단에 관여하지 않습니다.

두 시스템 다 같은 소스 파일(scenario_catalog.json, standard_guide.md)에서 만들어지지만 완전히 별개의 인덱스입니다. MCP 쪽은 manage.py import-catalog/import-guideline(매 실행 자동), Dify 쪽은 sync_dify_knowledge.py(자동 재실행 안 됨 — 문서 내용을 바꿨으면 수동 재실행 필요).
